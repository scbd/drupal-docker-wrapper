# Drupal Docker Wrapper

The ubiquitous language of this repository: a reusable Drupal 11 base Docker image that pins
contrib modules at build time and re-asserts that pinning at container startup. Build-time assembly
and runtime provisioning are two phases of one model, so they share this single glossary.

## Language

**Wrapper image**:
The Drupal 11 Docker image this repo builds (`scbd/drupal-docker-wrapper`). It layers pinned contrib
modules, Drush, CLI tools, and a two-phase startup on top of the upstream `drupal:11.x-php8.4` image.
_Avoid_: base image (that term is reserved for the upstream image), Drupal container.

**Upstream image**:
The official `drupal:<core>-php8.4` image the wrapper builds `FROM`. Its version is what the
wrapper's own version tracks.
_Avoid_: base image, parent image.

**Build stage**:
One named target in the multi-stage `Dockerfile` (`base-core`, `with-modules`, `final`). Each stage
adds one concern: core plus system packages, then pinned modules, then labels and runtime wiring.
_Avoid_: layer (a layer is a single instruction's filesystem delta, not a stage), step.

**Contrib module**:
A community-contributed Drupal module pinned to an exact version in the `with-modules` stage's
single `composer require`. Contrib ships inside the image; it is not custom code.
_Avoid_: plugin, extension, package (package is the Composer-level term).

**Custom module**:
A Drupal module owned by the bioland system and developed in its own repo (e.g. `bioland`, the
`scbd_*` modules). Custom modules are NOT part of the wrapper image; they are overlaid at runtime
from the host or EFS.
_Avoid_: site module, local module.

**Pinned version**:
An exact, non-floating version string for every contrib module and for Drush, declared inline in
the `Dockerfile`. Pinning is what makes the image reproducible.
_Avoid_: locked version (the lockfile records the resolved result; the pin is the declared intent).

**modules-versions.txt**:
The manifest of direct dependency versions, generated by `composer show --direct` during the
`with-modules` stage and written to `/opt/drupal/modules-versions.txt` for quick inspection.
_Avoid_: manifest, version file, dependency list.

**Integrity hash**:
A SHA256 written per contrib module during the build (`.<module>.hash` under `modules/contrib`),
computed over that module's `.php`, `.info.yml`, and `composer.json` files. These are build-time
artifacts only; no runtime script reads them today. After-start module repair detects drift by
comparing installed versions against `composer.lock` (plus ownership and `.info.yml` presence),
not via these hashes.
_Avoid_: checksum, fingerprint.

**Two-phase startup**:
The container's startup design: an immediate entrypoint phase that starts Apache, and a deferred
after-start phase (~60s later) that does the heavy provisioning in the background.
_Avoid_: boot sequence, init flow.

**Entrypoint phase**:
Phase one. `entrypoint.sh` runs as root, forks the after-start script, and chains to the upstream
Drupal entrypoint so Apache is serving immediately. It is intentionally thin.
_Avoid_: init script, startup script.

**After-start phase**:
Phase two. `after-start.sh` runs ~60 seconds after Apache, in the background, doing module repair,
deprecated-path cleanup, permission hardening, and cache rebuild. Gated so its one-time work runs
once per container start per image version.
_Avoid_: post-start hook, background job, cron.

**Version marker**:
The file `/tmp/after-start-<version>.complete` whose presence tells the after-start phase its
one-time work is already done for this image version. The version is read from `package.json`. On a
new run, stale markers from other versions are cleared first.
_Avoid_: lock file (that collides with composer.lock), sentinel, flag file.

**Module repair**:
The after-start step that walks every contrib module, compares each installed version against
`composer.lock`, removes any stale or mis-owned module directory, and runs `composer install` (as
www-data) to restore the pinned versions. It exists to re-sync a volume-mounted module tree against
the image.
_Avoid_: module reinstall, module sync, self-heal.

**Permission hardening**:
The after-start step that makes code read-only (`root:www-data`, dirs 755 / files 644), locks
`temp/` to `root:root` 700, fixes every `.htaccess` to 644, and leaves only `sites/*/files`
writable (`www-data:www-data` 775).
_Avoid_: chown pass, lockdown, securing.

**Privilege separation**:
The rule that root is used only to fix permissions and bind port 80, after which composer, Drush,
and cache work run as www-data (via gosu). Code is owned read-only by `root:www-data`, never
writable by the web user.
_Avoid_: drop privileges, sandboxing.

**Patch application**:
The mechanism for applying Drupal patches at container start (`scripts/lib/patches.sh`), trying
increasingly permissive `patch` strategies and marking each applied patch. It is currently
DISABLED: the `apply_patches_if_present` call is commented out in `entrypoint.sh`, so bundled
patches are not auto-applied at startup. Composer-level patching via `cweagans/composer-patches`
remains enabled at build time.
_Avoid_: hotfix, runtime patch (be specific: startup patch application vs composer patching).

**Volume mask**:
The runtime problem where bind-mounting the whole host/EFS `modules` directory over
`/opt/drupal/web/modules` hides the image's pinned contrib and integrity hashes, defeating the pin.
The fix is to mount only `modules/custom`.
_Avoid_: mount shadow, override.

**Wrapper version**:
The image's own version, in `package.json` and the release git tag, which tracks the Drupal core
version it ships. A bare core version (e.g. `11.4.1`) for a core bump; a `-vN` suffix for a later
wrapper iteration on the same core (a module bump, script change, or dependency update).
_Avoid_: image version, release number (be specific: this tracks core, with a wrapper suffix).
