# Drupal Docker Wrapper

The ubiquitous language of this repo: a reusable Drupal 11 base Docker image that pins contrib
modules at build time and keeps that pin intact through a mount contract that never bind-mounts
contrib at runtime. Build-time assembly and runtime provisioning are two phases of one model, so
they share this glossary.

## Language

**Wrapper image**:
The Drupal 11 image this repo builds (`scbd/drupal-docker-wrapper`): pinned contrib modules, Drush,
CLI tools, and a two-phase startup on top of `drupal:11.x-php8.4`.
_Avoid_: base image (reserved for the upstream image), Drupal container.

**Upstream image**:
The official `drupal:<core>-php8.4` image the wrapper builds `FROM`. Its version is what the
wrapper's own version tracks.
_Avoid_: base image, parent image.

**Build stage**:
One named target in the multi-stage `Dockerfile` (`base-core`, `with-modules`, `final`). Each adds
one concern: core plus system packages, then pinned modules, then labels and runtime wiring.
_Avoid_: layer (a layer is one instruction's filesystem delta, not a stage), step.

**Contrib module**:
A community module pinned to an exact version in the `with-modules` stage's single
`composer require`. Contrib ships inside the image; it is not custom code.
_Avoid_: plugin, extension, package (package is the Composer-level term).

**Custom module**:
A module owned by the bioland system, in its own repo (e.g. `bioland`, the `scbd_*` modules).
Custom modules are NOT in the wrapper image; they are overlaid at runtime from the host or EFS.
_Avoid_: site module, local module.

**Pinned version**:
An exact, non-floating version string for every contrib module and for Drush, declared inline in the
`Dockerfile`. Pinning is what makes the image reproducible.
_Avoid_: locked version (the lockfile records the resolved result; the pin is the declared intent).

**modules-versions.txt**:
The manifest of direct dependency versions, generated by `composer show --direct` during the
`with-modules` stage and written to `/opt/drupal/modules-versions.txt`.
_Avoid_: manifest, version file, dependency list.

**Integrity hash** _(removed)_:
A per-module SHA256 the build wrote under `modules/contrib`. Removed: nothing read it, and the
`find` expression generating it was mis-parenthesised, so it never verified anything.
`modules-versions.txt` remains the real manifest.
_Avoid_: claiming any runtime script reads or verifies these hashes today.

**Two-phase startup**:
An immediate entrypoint phase that starts Apache, and a deferred after-start phase that runs once a
readiness poll confirms the web server answers, doing heavy provisioning in the background.
_Avoid_: boot sequence, init flow, fixed sleep (it polls; it no longer sleeps a fixed duration).

**Entrypoint phase**:
Phase one. `entrypoint.sh` runs as root, forks a background job that polls for readiness then runs
after-start, and chains to the upstream Drupal entrypoint so Apache serves immediately.
Intentionally thin.
_Avoid_: init script, startup script.

**After-start phase**:
Phase two. `after-start.sh` runs once the readiness poll confirms the web server answers (or times
out), doing deprecated-path cleanup and image-code permission hardening. Both run on every start,
ungated. It touches no bind mount. There is no cache rebuild step; see **Cache rebuild**.
_Avoid_: post-start hook, background job, cron, module repair (removed - see **Module repair**),
cache rebuild (removed - see **Cache rebuild**), "runs once per container" or "once per version"
(nothing is gated any more - see **Version marker**).

**Version marker** _(removed)_:
A former file `<marker-dir>/after-start-<version>.complete` that told after-start the `sites/`
permission pass was already done for this image version on this volume. Removed with the work it
gated: after-start no longer touches a bind mount, so the remaining pass is cheap local-disk work
and a marker could only ever be wrong in the unsafe direction. See
[adr/0009](adr/0009-confine-after-start-to-image-code.md).
_Avoid_: describing any marker, marker directory, `MARKER_DIR`/`MARKER_FILE`, stale-marker purge, or
"once per version per volume" behaviour as present in `after-start.sh` today.

**Module repair** _(removed)_:
A former after-start step that compared installed contrib versions against `composer.lock` and ran
`composer install` at runtime. Removed: contrib is never bind-mounted (only `modules/custom` is -
see **Mount contract**), so it cannot drift.
_Avoid_: describing this as present, opt-in, or a fallback.

**Cache rebuild** _(removed from after-start)_:
A former after-start step that ran `drush cache:rebuild` with no site URI. Removed: without a URI
drush bootstraps only the default site, and the step was gated on `web/sites/default/settings.php`
existing, which a multisite install may not have. Under multisite - the only topology this image
runs - it was either a no-op or it rebuilt one arbitrary site. See
[adr/0007](adr/0007-remove-broken-multisite-cache-rebuild-from-after-start.md). A cache rebuild
after an image change is still needed; it is now an operator/deploy responsibility, run per site
through the mounted drush aliases (see **Mount contract**).
_Avoid_: describing this as still present in `after-start.sh`, or as automatic.

**Permission hardening**:
The after-start step (`harden_image_code`) making the image's own code read-only (`root:www-data`,
dirs 755 / files 644, which covers `.htaccess` files in those trees) across `web/core`,
`web/modules/contrib`, `web/themes`, `web/profiles`, `web/libraries`, `vendor`, and the root-level
`web/*` files, then restoring the execute bit on `vendor/bin` entries and their targets. It touches
nothing under the five bind mounts: `settings*.php` and `services*.yml` permissions are the deploy's
responsibility. See [adr/0009](adr/0009-confine-after-start-to-image-code.md).
_Avoid_: chown pass, lockdown, securing, `harden_mounted_volumes` (renamed), claiming this touches
`web/sites`, `modules/custom`, `drush` or `temp`, or that anything in the container tightens
`settings*.php`/`services*.yml` to `440`.

**.htaccess pass** _(removed from after-start)_:
A former step that walked every directory under the project root for files named `.htaccess`, to
`chown root:www-data` and `chmod 644` them. Removed: the walk crossed the EFS-backed
`sites/*/files` upload trees on every start and changed nothing durable. Code-path and root-level
`.htaccess` files were already covered by the chmod passes above it, and the one file it uniquely
touched, `sites/*/files/.htaccess`, sits on a bind mount the container no longer writes to. See
[adr/0008](adr/0008-remove-htaccess-hardening-from-after-start.md). Per-site `.htaccess` hardening,
where wanted, is now an external, operator-owned script outside this repo.
_Avoid_: describing this as present in `harden_image_code`, or as covering `sites/*/files`.

**Privilege separation**:
Root is used only to fix permissions and bind port 80; drush and other operator commands then run as
www-data (via gosu, invoked by hand). Code is owned read-only by `root:www-data`, never writable by
the web user.
_Avoid_: drop privileges, sandboxing.

**Patch application**:
Applying Drupal patches at container start (`scripts/lib/patches.sh`), using `git apply -p1` and
nothing else. No marker files: an already-applied patch is detected by a
`git apply --reverse --check` dry run and skipped. It is optional, not disabled: `entrypoint.sh` calls
`apply_patches_if_present` whenever `lib/patches.sh` is in the image, and logs and continues if the
patch engine or a step is missing or fails, so a missing patch layer never stops the container from
serving. Composer-level patching via `cweagans/composer-patches` remains enabled at build time.
_Avoid_: hotfix, runtime patch (be specific: startup patch application vs composer patching);
`patch(1)` fallback, applied markers, fuzz or multi-strategy application (none of these exist).

**Mount contract**:
The exact five paths the deployed Swarm stack bind-mounts per site: `php/custom.ini`,
`modules/custom`, `sites`, `drush`, and `temp`. Nothing else is ever mounted, so
`web/modules/contrib`, `web/core`, and `vendor` always come from the image and cannot drift at
runtime. `/var/www/html` is a symlink to `/opt/drupal/web`, so `/var/www/html/modules/custom` is
`/opt/drupal/web/modules/custom`.
_Avoid_: volume mask (retired term for a risk this contract makes structurally impossible).

**Volume mask** _(retired term)_:
An old name for bind-mounting the whole `modules` directory over the image's pinned contrib,
defeating the pin. Not possible under the **Mount contract**: only `modules/custom` is ever mounted.
_Avoid_: describing this as a current or future risk; it is structurally impossible today.

**Wrapper version**:
The image's own version, in `package.json` and the release git tag, tracking the Drupal core version
it ships. A bare core version (e.g. `11.4.5`) for a core bump; a `-vN` suffix for a later wrapper
iteration on the same core (a module bump, script change, or dependency update). The authoritative
value is the `version` field in `package.json`.
_Avoid_: image version, release number (be specific: this tracks core, with a wrapper suffix).
